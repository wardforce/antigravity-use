# 使用 AGY 编排数据库—后端—前端—端到端工作流的执行方案

## 1. 编排策略与完成标准

由高阶 Codex 主模型担任编排者：负责读取仓库约束、保护用户已有改动、拆分步骤、冻结跨层契约、检查每个真实 diff、亲自运行验收命令并给出最终结论。AGY 只执行边界清楚的步骤，AGY 的退出码、`status: SUCCESS` 或文字总结均不视为完成证据。

整个流程采用严格串行：数据库字段决定后端持久化与 API 契约，API 契约决定前端字段与交互，三层完成后才能做端到端验证。任何一步未通过，都停留在该步骤返工，不让下游基于未验收的契约继续。

完成条件是：四个阶段各自验收通过；完整 diff 只包含批准范围内的新增改动；用户原有未提交改动逐项保持；迁移可正向执行且按项目策略验证回滚或兼容性；后端接口测试、前端类型检查和组件测试、最终端到端场景全部通过。

## 2. 执行前：建立不可丢失的基线

主模型先读取仓库内全部适用指令（如根目录和子目录中的 `AGENTS.md`、贡献指南、迁移约定），识别实际技术栈、包管理器、数据库迁移工具、测试入口、前后端目录及现有 E2E 框架。此阶段只读，不改项目文件。

随后记录：

- 当前分支与 HEAD；
- `git status --short`；
- 已暂存 diff、未暂存 diff、未跟踪文件清单；
- 与目标文件重叠的用户已有改动及必要的内容哈希；
- 数据库、后端、前端和 E2E 的当前相关测试状态。

基线只用于比较，不执行 `stash`、`reset`、`checkout`、清理未跟踪文件或覆盖用户改动。若目标文件已有用户改动，步骤合同会明确要求保留这些基线 hunks；若无法可靠区分，主模型先缩小允许写入范围或亲自处理冲突部分，不把模糊所有权交给 AGY。

主模型在每一次新的 AGY 调用前重新运行 `agy models`，只从实时返回的 slug 中选择足以完成该步骤的最低成本模型，不依赖静态快照，也不猜测失效别名。一般以当前最新 Flash 的 medium 档承担边界清楚的多文件实现；机械搜索或小型测试可用 low；只有验收证明确属推理不足时才升到 high，复杂迁移设计才考虑实时可用的 Pro。切换模型家族时记录原因。若 slug 报 unknown model，刷新 `agy models` 后重新选择，不静默跨家族降级。

主模型先完成一次只读依赖调查，确定每步精确的读取/写入文件集合、验证命令和跨层契约。必要时可用 AGY 辅助只读调查：

```powershell
agy --model <LIVE_MODEL_SLUG> --mode plan --output-format json --print "<READ_ONLY_DISCOVERY_CONTRACT>"
```

只读调查可以并行，但主模型必须先汇总并冻结结果，才开始任何写入。本任务的四个写入/验证阶段不并行。

## 3. 每次委派的统一步骤合同

每个 AGY 提示都包含以下固定字段，且精确到本步骤：

```text
目标：本步骤唯一、可验收的结果。
上下文：技术栈，以及上一阶段已经由主模型验收并冻结的契约。
允许读取：完成本步骤所需的明确目录或文件。
允许写入：预先识别的精确文件清单或边界清楚的路径集合。
保持不变：用户基线改动、范围外文件、尚未授权变化的公开接口和既有行为。
验收：AGY 应运行的具体命令及预期结果。
返回：完成摘要、检查文件、修改文件、命令与结果、遗留问题和任何越界情况。
```

实现调用统一从目标仓库根目录运行，并保留 AGY 默认权限审查：

```powershell
agy --model <LIVE_MODEL_SLUG> --mode accept-edits --output-format json --print "<STEP_CONTRACT>"
```

不添加 `--dangerously-skip-permissions`。只有确需仓库外目录时才显式使用 `--add-dir`。主模型解析并保存每步 JSON 中的 `conversation_id`、`status`、`response`、`error`、`duration_seconds`、`num_turns` 和 `usage`；这些记录放在会话或临时位置，不污染项目工作树。

## 4. 阶段一：数据库字段迁移

### 委派目标

AGY 只实现数据库层变更：按项目现有迁移机制新增迁移，必要时同步 schema、ORM model 或数据库级测试。允许写入范围在只读调查后精确列出，例如新的迁移文件、对应 schema/model 文件和迁移测试；禁止修改控制器、业务 API、前端与无关配置。

合同中固定字段名称、类型、是否为空、默认值、索引/约束、历史数据处理方式、部署兼容顺序以及项目要求的回滚策略。AGY 必须检查已有数据场景，避免只对空库成立。

### 主模型验收门

AGY 返回后，主模型：

1. 与执行前基线比较，列出本阶段新增变更；
2. 阅读完整迁移 diff，确认写入范围、迁移顺序、幂等/回滚或向前兼容策略、历史数据处理和约束均正确；
3. 亲自运行项目实际的迁移测试：至少包含从基线 schema 正向升级、已有数据升级验证，以及项目支持时的 down/up 或等价回滚验证；
4. 运行相关数据库/ORM 测试并核对实际 schema；
5. 核对 AGY 报告的文件与命令和工作区实况一致；
6. 重新核对用户原有改动的 hunks、暂存状态和未跟踪文件仍完整。

六项均通过后，冻结“数据库字段契约”，包括字段定义、约束、默认值、读写语义及部署兼容要求，作为后端阶段的不可自行改写输入。

## 5. 阶段二：后端接口适配

### 委派目标

刷新 `agy models` 后选择实时模型。AGY 依据已验收的数据库字段契约，最小化适配持久化映射、领域/服务逻辑、请求与响应 DTO、校验、序列化及接口测试。允许写入范围只包含调查确认的后端实现和测试文件；数据库迁移契约、前端和范围外公开接口保持不变。若兼容性要求存在，明确旧客户端缺省该字段时的行为及新旧响应语义。

### 主模型验收门

主模型逐项检查本阶段相对基线的新增 diff，重点验证：字段映射没有遗漏；缺失值、非法值、空值、默认值和权限边界正确；请求/响应契约与数据库契约一致；没有顺手重构或扩大公开接口。随后亲自运行后端单元测试、接口/集成测试、静态检查或编译，并在测试数据库上验证一次真实读写闭环。再次确认原有用户改动完整。

全部通过后冻结“API 契约”：字段名与类型、是否必填、默认行为、校验错误、响应形状和兼容规则。前端只能消费该契约，不能自行推断或重新定义。

## 6. 阶段三：前端表单更新

### 委派目标

再次刷新 `agy models`。AGY 依据已验收 API 契约更新表单字段、初始值、前端类型、校验、提交 payload、编辑态回填、错误展示及必要的组件测试。允许写入范围只包含确认过的前端组件、类型/客户端封装和测试文件；不得修改数据库、后端或无关 UI。提示中明确现有设计系统、可访问性约定和用户已有 UI 改动必须保留。

### 主模型验收门

主模型检查完整 UI diff 和实际行为，覆盖新建、编辑回填、有效提交、必填/非法值、后端错误显示、取消或重复提交等适用边界；确认 payload 与 API 契约逐字段一致且没有破坏旧流程。主模型亲自运行格式/静态检查、类型检查、前端单元或组件测试以及生产构建，并在真实浏览器中做目标表单的最小交互验证。然后再次核对用户基线改动完整。

通过后冻结“用户流程契约”，包括页面入口、输入步骤、请求、成功反馈、刷新后持久化结果和错误路径，供 E2E 验证直接使用。

## 7. 阶段四：端到端验证与完整审查

最终验收由主模型负责，不把 AGY 的自测报告当作结论。主模型先确认测试服务、数据库和前端均使用当前工作树，再执行既有 E2E 测试或按冻结的用户流程补充最小、稳定的 E2E 用例（若需新增测试文件，可作为独立 AGY 实现步骤，给出精确写入范围，并经过同样审查门）。

端到端场景至少验证：

1. 从页面打开表单并正确显示新字段；
2. 填写并提交后，请求 payload 符合冻结的 API 契约；
3. 后端成功落库，数据库值和约束符合迁移契约；
4. 页面显示成功状态，重新加载或进入编辑态后能正确回填；
5. 至少一个关键无效输入或后端校验失败路径能给出正确反馈；
6. 既有核心流程回归测试未被破坏。

主模型最后查看从最初基线到当前状态的完整 diff，运行覆盖数据库、后端、前端和 E2E 的最全面相关验证，并再次比对最初的 staged/unstaged/untracked 基线。只有实际命令成功、用户可见流程成功、变更未越界且用户原有改动完整，才判定任务完成。

## 8. 失败、部分写入与返工闭环

若 AGY 非零退出或返回 `status: ERROR`，主模型先检查 stderr、`error`、工作区真实状态以及是否发生部分写入；不直接重跑，也不让下一阶段开始。若实现存在可修复问题，使用该步骤第一次返回的 `conversation_id` 和同一个实时模型 slug 返工：

```powershell
agy --conversation <CONVERSATION_ID> --model <SAME_LIVE_MODEL_SLUG> --mode accept-edits --output-format json --print "<具体失败证据 + 原允许写入范围 + 不变的原验收条件>"
```

返工提示必须给出具体的失败测试、错误输出、diff 位置或越界文件，不能只说“再检查”。返工后从头执行六项主模型审查门，并确认 `num_turns` 确实增长。同一缺陷最多交给 AGY 修正两轮；若仍失败，由主模型接管最小必要修改并重新执行全部相关验收。只有当失败证明确属推理能力不足时，才在刷新 `agy models` 后升级推理档，并记录升级理由。

若发现越界写入，先识别哪些 hunks 属于本次 AGY；在不触碰用户基线改动的前提下撤销或最小修正本次越界部分，再以原合同返工。任何情况下都不通过重置整个文件或工作树来恢复。

## 9. 最终交付记录

最终回复应列出：实际完成的四阶段内容；每阶段采用的实时模型 slug 与选择理由；各 `conversation_id` 和是否发生返工；主模型实际运行的命令及结果；完整 diff 的范围；用户原有改动保持情况；以及仍存在的限制或未覆盖场景。没有真实 diff、真实测试和用户流程证据时，不声明完成。
