# 使用 AGY 编排数据库到前端的串行交付方案

## 1. 编排原则

这项工作应由主 Codex 负责任务拆分、范围控制和最终验收，AGY 只执行边界清晰、可独立验收的步骤。数据库迁移、后端契约、前端表单和端到端验证存在严格的前后依赖，因此默认串行执行；不会为了并发而让多个 AGY 会话同时改动共享文件或尚未稳定的接口。

AGY 返回成功、命令退出码为 0，只说明代理调用完成，不代表实现已验收。每个阶段结束后，主 Codex 都必须亲自检查工作区、差异和测试结果，通过门禁后才进入下一阶段。

## 2. 执行前建立只读基线

1. 读取仓库中的 `AGENTS.md`、开发文档、迁移规范、测试命令及包管理配置。
2. 运行 `agy models`，以实时输出选择模型 slug，不依赖记忆中的模型名称。迁移设计和跨层契约优先选择擅长长上下文与推理的可用模型；机械实现或聚焦测试可选成本更低的可用模型。
3. 记录但不改动以下基线：
   - `git status --short`；
   - 已跟踪文件的 `git diff` 和 `git diff --cached`；
   - 未跟踪文件清单；
   - 当前分支与 HEAD；
   - 与数据库、后端、前端和 E2E 有关的现有测试状态。
4. 建立“用户原有改动清单”，逐项记录文件路径和初始差异。整个流程禁止执行 `git stash`、`git reset`、`git checkout --`、清理未跟踪文件或覆盖式格式化。若用户改动与任务必改区域重叠，主 Codex先理解并把它作为当前基线保留；无法安全区分时暂停该写入步骤并请求用户决定。
5. 先由主 Codex确认实际技术栈、现有字段名、目标字段定义、兼容要求和回滚策略，形成四阶段的契约表。未确认的信息不会让 AGY 自行猜测。

## 3. 通用 AGY 调用协议

每一步从项目根目录单独启动一个 headless 调用，显式指定实时模型、执行模式和 JSON 输出。实际调用形态为：

```powershell
agy --print "<该阶段完整提示词>" --model <LIVE_MODEL_SLUG> --mode accept-edits --output-format json
```

只读调查使用 `--mode plan`；已批准且文件范围明确的实现才使用 `--mode accept-edits`。默认不使用 `--dangerously-skip-permissions`。提示词必须包含：阶段目标、允许读取范围、允许修改的精确路径/文件类型、禁止触碰的用户改动、上一步已验收的契约、验收命令，以及要求返回的结构。

每次保存 JSON 中的 `conversation_id`、`status`、`response`、`error` 和验证摘要。要求 AGY 明确报告：检查过的文件、修改过的文件、运行过的命令及结果、未解决问题、是否越界。非零退出码、`status: ERROR`、缺失结果或摘要与工作区不符都直接判为未通过。

## 4. 串行任务与逐步验收

### 阶段 A：数据库字段迁移

委派目标：按照项目现有迁移框架新增可回滚、向前兼容的字段迁移，并同步必要的数据库模型或 schema 定义。

- 允许范围：新迁移文件、与该字段直接对应的 schema/model 文件、迁移测试；不允许修改后端接口、前端或无关配置。
- 提示词重点：字段类型、空值/默认值、索引或约束、历史数据处理、部署顺序、回滚路径，以及兼容旧应用版本的要求。
- AGY 自检：迁移 up/down 或等价流程、空库迁移、已有数据升级、schema/迁移测试。
- 主 Codex 门禁：对照基线检查实际 diff；确认用户原改动逐字保留；审查迁移的锁表/数据丢失风险、幂等性和回滚；亲自运行最小迁移测试。只有数据库契约和字段语义固定后才进入阶段 B。

### 阶段 B：后端接口适配

委派目标：基于阶段 A 已验收的字段契约，更新持久化映射、校验、服务逻辑、请求/响应 DTO 和接口测试，同时维持约定的兼容策略。

- 允许范围：该接口直接相关的后端 controller/handler、DTO、service、repository/model 与测试；不得修改迁移和前端文件。
- 提示词输入：已验收字段名、类型、null/default 语义、序列化格式、错误响应和向后兼容规则。
- AGY 自检：后端单元/集成测试，至少覆盖字段缺省、合法值、非法值、读回一致性及旧请求兼容。
- 主 Codex 门禁：审查 API 契约、验证逻辑和数据库映射；检查是否出现越界重构；亲自运行相关后端测试并查看实际 diff。将最终请求/响应样例固化为阶段 C 的唯一接口契约。

### 阶段 C：前端表单更新

委派目标：严格按阶段 B 的已验收接口契约更新表单控件、初始值、客户端校验、提交载荷、编辑回填、错误提示和相关组件测试。

- 允许范围：目标表单组件、直接相关的类型/API client、文案和测试；不得改数据库迁移或后端实现。
- 提示词输入：后端最终字段名、可选性、格式、合法范围、错误结构，以及项目现有 UI/可访问性规范。
- AGY 自检：新增、编辑、清空/缺省、校验失败、后端错误展示和成功提交等组件测试；若项目有类型检查与 lint，也运行聚焦检查。
- 主 Codex 门禁：检查表单状态与 API payload 一致，确认没有硬编码旧契约，检查键盘操作、label/error 关联和加载状态；亲自运行前端测试、类型检查，并核对 diff 与用户原改动。

### 阶段 D：端到端验证

先使用一个独立的 AGY 只读审查会话（`--mode plan`）核对 A-C 的完整契约链并列出 E2E 场景。主 Codex 审核场景后，再开启实现会话，仅允许修改 E2E 测试及其必要 fixture。

E2E 至少验证：

1. 在真实测试数据库上应用迁移；
2. 通过 UI 新建带新字段的数据并观察成功状态；
3. 从后端/数据库读回并确认值与类型一致；
4. 刷新或重新进入编辑页，确认回填；
5. 修改并保存，确认更新持久化；
6. 覆盖缺省值、非法输入与服务端错误路径；
7. 在兼容策略要求下验证旧数据或旧请求。

主 Codex负责启动项目所需服务、亲自运行 E2E、检查浏览器控制台和服务端日志，并以最终平台/数据库状态判定成功，不把“点击完成”或 AGY 的文字报告当成成功证据。

## 5. 每一步的固定审查门

每个 AGY 会话返回后，主 Codex按相同顺序验收：

1. 比较 `git status` 与执行前基线，区分用户原改动和本阶段新增改动。
2. 核对所有新增变更都位于允许范围；发现越界立即阻止后续步骤。
3. 阅读完整 diff，检查正确性、最小性、数据/API 兼容性和是否混入无关格式化。
4. 独立运行该阶段约定的测试，不接受只转述 AGY 的测试结论。
5. 检查 AGY 报告与真实文件、命令输出一致。
6. 确认用户原有未提交改动没有被删除、覆盖或重写。
7. 记录通过的产物、契约和测试证据，作为下一步不可擅自更改的输入。

## 6. 返工、失败与接管

- 审查未通过时，使用原 `conversation_id` 恢复同一会话：

  ```powershell
  agy --conversation <CONVERSATION_ID> --print "<具体差异、失败输出、允许范围和不变的验收条件>" --model <SAME_LIVE_MODEL_SLUG> --mode accept-edits --output-format json
  ```

- 每次只反馈可复现的具体问题，不扩大文件范围；返工后从头执行该阶段审查门。
- 同一缺陷最多允许两轮 AGY 返工。仍不合格、持续越界或模型不可用时，停止委派，由主 Codex接管最小必要修正；在本次“仅输出方案”的场景中只记录该接管决策，不实施。
- 模型 slug 失效时重新运行 `agy models`，明确记录换用的模型及理由；认证、权限、超时或 JSON 错误要保留现场，先检查工作区是否已有部分写入，再决定恢复会话或停止。
- 任一步失败都不会继续下游步骤，因为后续实现依赖上一阶段已经验收的契约。

## 7. 最终整体验收与交付证据

A-D 均通过后，主 Codex进行一次全局验收：

- 核对最终完整 diff 与用户初始基线，确认原有改动仍保留且所有新增文件均在任务范围内；
- 从空库和带历史数据的数据库分别验证迁移与回滚；
- 运行后端全量相关测试、前端测试/类型检查/构建和完整 E2E；
- 检查数据库字段、后端 DTO、前端类型、表单 payload 和回填展示使用同一契约；
- 汇总每个 AGY 会话 ID、模型、变更文件、验证命令、实际结果、返工次数和剩余风险。

只有上述证据全部成立，主 Codex才报告任务完成。任何未运行、跳过或受环境阻塞的验证都应明确标注，不能用 AGY 的 `SUCCESS` 状态替代。
